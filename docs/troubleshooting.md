# Если подключение не работает

Начните с точного сообщения об ошибке в расширении. Значок **ON** подтверждает только применение настроек Chrome; для сетевой проверки используйте **Проверить внешний IP**. Не публикуйте ключ `shbvpn1:…`, файл `/etc/shbvpn/credentials`, приватный TLS-ключ и полный вывод команд, где они показаны.

## Установщик остановился

| Сообщение или симптом | Что проверить |
| --- | --- |
| Поддерживается только Ubuntu 24.04/26.04 | Выполните `. /etc/os-release; printf '%s %s\n' "$ID" "$VERSION_ID"`. На другой ОС установщик не запускается. |
| Порт 80 или порт прокси занят | Выполните `sudo ss -ltnp '( sport = :80 or sport = :443 or sport = :8443 )'`. Для занятого 443 выберите `--port 8443`; порт 80 должен быть свободен. |
| Certbot не выдал сертификат | Убедитесь, что адрес действительно принадлежит VPS, доменная A-запись указывает на него, а **80/TCP** доступен извне через файрвол провайдера и UFW. |
| Для IP требуется Certbot 5.4+ | Обновите выбранный Certbot backend и повторите ту же команду установки. Установщик не обновляет существующий snap автоматически. |
| На Ubuntu 26.04 не скачивается Certbot в venv | Проверьте доступ к PyPI и `python3-venv`. Этот вариант выбирается, когда `snapd.service` или `snapd.socket` замаскирован. |
| Служба или проверка продления завершилась ошибкой | Смотрите журнал и состояние служб по командам ниже. Установку можно повторить с прежними адресом и портом после устранения причины. |

Для просмотра состояния на VPS:

```bash
sudo systemctl status shbvpn-proxy.service shbvpn-acme.service shbvpn-renew.timer
sudo journalctl -u shbvpn-proxy.service -u shbvpn-acme.service -u shbvpn-renew.service -n 100 --no-pager
sudo systemctl list-timers shbvpn-renew.timer
```

Если при первом запуске установщик оборвался на середине, часть файлов и служб могла успеть появиться. Повторите команду установки **с теми же** `--ip`/`--domain` и `--port` после исправления причины. Если повторный запуск сообщает о конфликте ресурсов, проверьте их происхождение по журналу и [создайте issue](https://github.com/coffegorio/self-hosted-browser-vpn/issues) с обезличенным выводом; не удаляйте чужие службы или сертификаты вслепую.

## Сервер работает, но Chrome не подключается

1. Проверьте, что прокси активен и слушает нужный порт:

   ```bash
   sudo systemctl is-active shbvpn-proxy.service
   sudo ss -ltnp '( sport = :443 or sport = :8443 )'
   sudo python3 /usr/local/share/shbvpn/installer/healthcheck.py
   ```

   Локальная проверка должна сообщить `TLS, authentication and destination guard: OK`.

2. Проверьте входящий **выбранный TCP-порт** в панели VPS и во внешнем файрволе. Правило UFW само по себе не открывает порт в файрволе хостинг-провайдера. Для нестандартного порта также убедитесь, что сеть, из которой вы открываете Chrome, не блокирует его.
3. Проверьте сертификат и время на сервере:

   ```bash
   sudo openssl x509 -in /etc/shbvpn/tls/fullchain.pem -noout -dates -subject -issuer
   timedatectl status
   ```

   Сертификат должен соответствовать адресу в ключе и не быть просроченным. Не обходите проверку сертификата в Chrome.
4. Если вы меняли пароль через `sudo shbvpn --rotate`, импортируйте новый ключ через **Заменить сервер**. Ошибка авторизации `407` обычно указывает на неверные или старые учётные данные.
5. При статусе **Конфликт настроек** проверьте другие расширения с доступом к прокси и политики Chrome (`chrome://policy`). При ошибке ограничения WebRTC проверьте политики и расширения, управляющие настройками приватности.

Ошибка `403` от прокси обычно означает, что запрошен непубличный адрес или запрещённый порт назначения. Ошибка `502` указывает на неудачное DNS-разрешение или соединение от VPS до сайта. В реализации разрешены только порты сайтов `80`, `443`, `8080`, `8443` и `9443`.

## Проверка IP показала неожиданный адрес

Сначала убедитесь, что проверяете **тот же профиль Chrome**, где включено расширение. Откройте его всплывающее окно: должен быть статус **Маршрутизация включена**. Сервис `api.ipify.org` не должен находиться в исключениях. Сравнивайте результат с **исходящим** IP VPS: при NAT или IPv6 он может отличаться от адреса, по которому браузер подключается к прокси. Для независимого сравнения выполните на VPS:

```bash
curl -4 https://api.ipify.org
```

Если браузер показал IPv6, сравните с исходящим IPv6 сервера. Затем проверьте конкретный сайт: некоторые соединения Chrome, локальные адреса и явно исключённые домены не обязаны проходить через прокси. См. [границы маршрутизации](architecture.md).

## Сертификат скоро истечёт

Проверьте, что `shbvpn-renew.timer` активен, а **80/TCP** по-прежнему доступен извне. Для ручной диагностики можно повторить пробное продление. Оно запускает deploy hook и **кратко перезапускает прокси**:

Если `sudo cat /etc/shbvpn/certbot-backend` выводит `snap`:

```bash
sudo /snap/bin/certbot renew --dry-run --run-deploy-hooks --no-random-sleep-on-renew --cert-name shbvpn
```

Если выводит `venv`:

```bash
sudo /usr/local/share/shbvpn/certbot-venv/bin/certbot \
  --config-dir /etc/shbvpn/letsencrypt \
  --work-dir /var/lib/shbvpn/certbot-work \
  --logs-dir /var/log/shbvpn/certbot \
  renew --dry-run --run-deploy-hooks --no-random-sleep-on-renew --cert-name shbvpn
```

После проверки снова посмотрите срок действия сертификата и журнал `shbvpn-renew.service`. При коротком сроке IP-сертификата не откладывайте исправление ошибки продления.
