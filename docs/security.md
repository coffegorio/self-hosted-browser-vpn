# Безопасность и модель доверия

Сервер и расширение рассчитаны на личный хост с публичным входящим адресом, например VPS. Это не сервис анонимности и не замена системному VPN. Перед использованием для чувствительных задач оцените [границы маршрутизации](architecture.md) и проверьте свою сеть.

## Кому вы доверяете

Браузер устанавливает TLS-соединение с HTTPS-прокси на вашем хосте и проверяет его обычным хранилищем доверенных сертификатов. Прокси требует HTTP Basic-авторизацию внутри этого TLS-соединения. Хост прокси знает адреса назначения; для обычного HTTP он также видит содержимое запроса и ответа. При HTTPS через `CONNECT` содержимое сайта остаётся защищено отдельным TLS между браузером и сайтом, но адрес назначения виден прокси. Провайдер сети и внешние сайты могут видеть сетевые соединения и исходящий адрес хоста.

Расширение запрашивает разрешения Chrome `proxy`, `privacy`, `storage`, `webRequest`, `webRequestAuthProvider` и доступ к URL для авторизации на собственном прокси и проверки IP. Исходный код расширения находится в [`extension/`](../extension). Встроенная кнопка проверки отправляет запрос стороннему сервису `api.ipify.org`; без её нажатия этот тест не запускается.

## Ключ подключения

Ключ `shbvpn1:…` содержит адрес, порт, имя пользователя и **пароль** в JSON, закодированном base64url. Кодирование **не шифрует** данные. Любой получивший ключ может использовать ваш прокси до смены пароля.

- Не добавляйте ключ, файл `/etc/shbvpn/credentials` на Ubuntu или данные тома Docker `runtime` в Git, issue, логи CI, снимки экрана и чаты.
- Храните ключ как пароль. На Ubuntu без Docker получайте его командой `sudo shbvpn --show-key`; в контейнерной установке используйте [команду Compose `show-key`](../deploy/README.md#управление) только тогда, когда ключ нужен.
- Расширение хранит разобранный ключ в `chrome.storage.local` и ограничивает доступ доверенными контекстами расширения. Оно не шифрует файлы профиля Chrome. Защитите локальную учётную запись и диск компьютера.
- Если ключ раскрыт, смените пароль: `sudo shbvpn --rotate` на Ubuntu либо [Compose `rotate` с перезапуском `proxy`](../deploy/README.md#управление). Затем замените ключ в расширении. В контейнерном варианте прежний пароль перестаёт работать после перезапуска прокси.

Сервер принимает подключения со всех сетевых интерфейсов на выбранном порту; сильный случайный пароль генерируется при установке. Дополнительного ограничения по IP клиента, двухфакторной авторизации и ограничения частоты попыток в MVP нет. Защитите доступ к хосту и при необходимости ограничьте входящий порт своим файрволом, учитывая сети, из которых будете подключаться.

## Защита сервера

Сервер разрешает соединения только с публичными IP-адресами на портах `80`, `443`, `8080`, `8443` и `9443`. Он отклоняет локальные, частные, link-local, документированные тестовые и некоторые служебные диапазоны. Он также не соединяется с собственным публичным адресом из настройки прокси, адресами видимых ему сетевых интерфейсов и дополнительными адресами, указанными через `--self-address` или `SHBVPN_SELF_ADDRESSES`. Это защищает службы на самом хосте, доступ к которым извне закрыт файрволом провайдера. При работе процесса сервер запоминает уже обнаруженные DNS-адреса собственного домена, чтобы временная ошибка DNS или смена записи не сняла их защиту. После перезапуска доступны только текущая DNS-запись, видимые интерфейсы и явно заданные адреса. В Docker видны интерфейсы контейнера; другие публичные входящие адреса за NAT или floating IP нужно указывать явно. Определить все такие адреса автоматически невозможно. Сайт на заблокированном собственном IP через этот прокси не откроется.

При установке на Ubuntu службы прокси и ACME работают от отдельного пользователя `shbvpn` с ограничениями systemd. Установщик запускается с правами root, потому что устанавливает пакеты и службы и получает сертификат. В Compose контейнеры прокси и ACME работают без root, с файловой системой только для чтения; контейнер Certbot управляет томами с правами root. Docker socket в контейнеры не передаётся. Защитите доступ к Docker: пользователь с правом управлять контейнерами и томами может прочитать ключ и приватный TLS-ключ. Проверяйте код и изменения перед повторной установкой из обновлённого репозитория.

На Ubuntu сертификат Let's Encrypt проверяется на продление таймером `shbvpn-renew.timer`; в Compose — циклом `cert-manager`. Оба варианта сверяют установленный сертификат с Certbot и проверяют ответ работающего прокси. Для IP-сертификатов срок действия короткий; оставьте **80/TCP** открытым для HTTP-01 и контролируйте `shbvpn-renew.service` либо контейнер `cert-manager`. Не отключайте проверку TLS-сертификата в браузере и не используйте самоподписанный сертификат как постоянную замену.

## Что расширение не гарантирует

PAC-правило содержит только прокси для обычных сайтов и `DIRECT` для ваших исключений; запасного прямого маршрута для проксируемых сайтов в нём нет. При этом Chrome может обходить прокси для локальных адресов и собственных операций. DNS, IPv6, WebRTC, инкогнито и конфликты настроек требуют проверки на конкретной системе. Ограничение прямого UDP для WebRTC может нарушить работу видеозвонков. UDP/QUIC сервер не проксирует.

Статус **ON** подтверждает настройки Chrome, а не полную приватность и не доступность сервера. Проверяйте внешний IP и поведение нужных сайтов. Если Chrome сообщает о возможном прямом соединении или конфликте, расширение показывает ошибку; считайте такую ситуацию требующей диагностики.

## Сообщить об уязвимости

Не публикуйте рабочие ключи и приватные данные в открытом issue. Если в репозитории включена функция GitHub **Private vulnerability reporting**, используйте её для непубличного сообщения; иначе создайте issue без эксплуатационных подробностей и попросите владельца проекта указать приватный канал связи.
